# DeckAtlas 产品化与工程化推进方案

## 1. 结论先行

DeckAtlas 已经完成了从“脚本集合”到“可用本地工具”的跨越，但距离可长期推广的成熟产品，
还差三层能力：

1. **产品闭环**：用户不仅能导入、选片和导出，还能理解数据放在哪里、占了多少空间、
   当前是否健康、失败后如何恢复。
2. **工程边界**：Electron、CLI、数据库、渲染器和文件系统要有清晰职责，所有重任务进入
   同一套队列、状态机和恢复机制。
3. **发布能力**：应用必须脱离源码仓库和开发环境独立运行，具备签名、升级、迁移、
   诊断和回滚能力。

建议采用“双轨一底座”：

- 产品化轨：围绕“资料进入 → 找到 → 选中 → 导出 → 持续维护”重构信息架构。
- 工程化轨：围绕“任务、数据、渲染、发布、观测”拆分边界。
- 共同底座：本地优先、源文件不复制、操作可解释、失败可恢复。

## 2. 产品定位

### 2.1 一句话

DeckAtlas 是面向高频做方案人群的本地演示素材工作台：把散落在文件夹里的 PPT 拆成可搜索、
可预览、可复用的页面，并安全组合成新稿。

### 2.2 首要用户

第一阶段只服务一类人：本机有大量历史 PPT、每周都要找页和拼稿、又不能把源文件上传
云端的售前、市场、咨询和管理者。

这类用户的核心任务不是“管理文件”，而是：

- 在几千页历史材料中快速找到一页。
- 判断这一页是否最新、可用、可导出。
- 把跨文件页面按顺序拼成新稿。
- 让素材库持续跟随原目录变化。

### 2.3 核心价值

| 使用前 | DeckAtlas 如何解决 | 使用后 |
| --- | --- | --- |
| 靠文件名和记忆翻几十份 PPT | 页级索引、缩略图、分类和搜索 | 分钟级找到可复用页面 |
| 复制粘贴容易丢主题、颜色和媒体 | OOXML 原生组合与源哈希校验 | 页面保真、来源可追踪 |
| 新旧版本混在文件夹里 | 自动更新、移动识别、历史记录 | 页库持续可信 |
| 不知道后台改了什么 | 预检、任务进度、失败原因 | 用户始终掌握影响范围 |

### 2.4 明确不做

- 不做通用网盘或企业内容管理系统。
- 不在 V1 上传源 PPTX。
- 不做不可见的系统级后台任务。
- 不默认自动删除源文件已消失的页库内容。
- 不以“AI 自动生成整套 PPT”替代人工选片与判断。
- HTML 在能力稳定前不承诺直接组合为 PPTX。

## 3. 核心产品闭环

### 3.1 北极星用户任务

DeckAtlas 的核心不是“导入 PPT”，而是帮助用户完成一条稳定、可重复的生产链路：

> 资料进入 → 找到合适页面 → 判断页面是否可信 → 加入选片 → 导出新稿 → 持续维护

这个闭环是后续功能取舍的最高原则。任何新增功能至少要提升以下一个指标：

- 找得更快。
- 判断成本更低。
- 复用结果更可靠。
- 导出成功率更高。
- 素材维护成本更低。

不能证明改善闭环的功能，不进入 P0/P1。

### 3.2 六个关键阶段

| 阶段 | 用户问题 | 产品必须给出的答案 | 成功信号 |
| --- | --- | --- | --- |
| 资料进入 | 哪些内容会进入页库 | 范围、格式、大小、空间影响 | 首次导入完成 |
| 持续更新 | 页库是不是最新 | 上次扫描、变更、失效源 | 更新无需重复劳动 |
| 找到页面 | 我需要的页在哪里 | 搜索、筛选、目录和上下文 | 搜索后打开/选中 |
| 判断可信 | 这页现在还能不能用 | 来源、版本、预览、导出状态 | 用户无需打开源稿确认 |
| 组织选片 | 这些页如何组成故事 | 顺序、来源、冲突和版本提醒 | 形成可导出选片单 |
| 交付结果 | 新稿是否正确可用 | 预检、保真、体积、来源清单 | 一次导出成功 |

### 3.3 核心产品对象

产品界面和数据模型应围绕七个稳定对象设计，避免把缓存、哈希、进程等实现概念暴露给用户：

| 对象 | 用户理解 |
| --- | --- |
| 资料目录 | 用户授权给 DeckAtlas 维护的内容边界 |
| 文件 | 一份可追踪版本和来源状态的演示文稿 |
| 页面 | 最小检索、判断和复用单元 |
| 选片单 | 面向一个具体出稿任务的页面集合 |
| 导出稿 | 一次有来源、有状态的交付结果 |
| 扫描计划 | 资料目录持续更新的规则 |
| 任务 | 导入、渲染、扫描、清理和导出的执行记录 |

### 3.4 闭环优先级

产品首页不应强调“系统有多少功能”，而应优先帮助用户继续未完成任务：

1. 有未完成选片单：继续选片或导出。
2. 有失效来源或失败任务：先处理风险。
3. 页库为空：进入首次导入。
4. 页库健康：直接搜索和浏览。

## 4. 页面可信度体系

### 4.1 产品目标

页级搜索只解决“找得到”。成熟产品还必须让用户在不打开源 PPT 的情况下判断：

- 这是不是当前版本。
- 页面是否完整渲染。
- 能否安全导出。
- 来源是否仍然存在。
- 使用后会不会出现字体、媒体或链接问题。

可信度不是一个模糊分数，而是一组可解释状态。

### 4.2 四个可信维度

| 维度 | 状态 | 判定依据 |
| --- | --- | --- |
| 新鲜度 | 最新 / 源文件已变化 / 待重新扫描 | 路径、mtime、ctime、SHA-256 |
| 来源可用性 | 可用 / 已移动 / 不可用 / 待授权 | 文件存在性与目录授权 |
| 预览完整性 | 完整 / 待修复 / 渲染失败 | 缩略图、高清图、缓存版本 |
| 导出兼容性 | 可原生导出 / 有风险 / 不可导出 | 格式、尺寸、外链、视频、OLE |

### 4.3 页面状态表达

列表卡片只显示最高优先级状态，避免徽标堆积：

1. `不可导出`
2. `源文件不可用`
3. `源文件已变化`
4. `预览需修复`
5. `可用`

页面详情再展示完整证据，包括来源路径、文件更新时间、入库时间、版本摘要、保真等级和
问题原因。状态必须配文字，不能只依赖颜色。

### 4.4 关键规则

- 页面状态变化不静默替换用户选片。
- 源文件变化后，旧选片明确提示“版本已过期”。
- 导出前重新检查来源与兼容性，不能只相信入库时状态。
- 自动更新失败时保留最后一份可用预览。
- 所有风险提示都给出下一步动作，而不只给错误码。
- “保真等级 A/B”要解释差异，例如外链保留、视频兼容或字体替换。

### 4.5 可信度指标

- 可用页面占比。
- 来源失效率。
- 预览完整率。
- 导出前风险拦截率。
- 因版本变化导致的导出失败率。
- 用户需要返回源 PPT 二次确认的比例。

## 5. 成熟产品的信息架构

当前“1-5 步”导航把长期维护能力误表达成线性流程。建议重构为三个工作区：

### 创作

- **素材库**：浏览、搜索、筛选、查看文件与页面。
- **选片单**：跨文件收集、排序、版本提醒。
- **组合导出**：输出设置、兼容性检查、结果与来源清单。

### 维护

- **导入与更新**：手动导入、自动更新、运行中任务。
- **重复与质量**：重复页、失效源、异常预览、低置信分类。

### 系统

- **设置与存储**：路径、空间、缓存、渲染器、性能和通知。
- **诊断与关于**：环境检查、日志导出、版本、升级和隐私说明。

不建议继续增加更多编号步骤。编号适合一次性向导，不适合日常工作台。

## 6. 产品化重点

### 6.1 设置中心

建议新增独立设置模块，而不是把参数散落到各页面。

设置中心的原则是“暴露用户决策，不暴露实现细节”。默认层只回答数据放哪里、质量与
空间如何取舍、何时更新、源文件失效后如何处理；LibreOffice 路径、缓存版本、超时秒数
等技术参数进入“高级设置”或诊断页。

| 分组 | 必须提供的配置 |
| --- | --- |
| 通用 | 启动时打开页面、默认导出目录、语言、主题 |
| 页库 | 数据目录、数据库位置、缩略图质量、预览质量 |
| 渲染 | 当前引擎、LibreOffice 可用性、单任务模式、超时 |
| 自动更新 | 总开关、默认时间窗、文件稳定等待、历史保留天数 |
| 隐私 | 本地处理说明、外链媒体策略、诊断包包含内容 |
| 更新 | 当前版本、检查更新、发布渠道、回滚入口 |

配置修改分三类：

- 即时生效：主题、默认页面、通知。
- 下次任务生效：渲染质量、自动更新规则。
- 需要迁移或重启：数据目录、运行时、数据库升级。

### 6.2 存储中心

用户关心的不是一个总数字，而是“什么占空间、能否清、清了有什么影响”。

应展示：

- 源文件：只统计引用，不计入 DeckAtlas 占用，不允许删除。
- 数据库与索引。
- 缩略图。
- 高清预览。
- HTML 安全副本与媒体。
- 临时文件。
- 导出文件。
- 可安全释放空间。

清理动作必须先预估影响：

- 清理临时文件：安全，可直接执行。
- 清理可重建预览：展示释放空间和下次重建成本。
- 清理失效版本：检查选片单引用后执行。
- 移动数据目录：校验目标空间，复制、校验、切换、保留回滚点。

### 6.3 任务中心

自动更新不是唯一后台任务。成熟产品应把导入、渲染、组合、重复扫描、缓存清理统一为
“任务中心”：

- 当前任务与排队任务。
- 阶段、文件、页面、耗时和预计剩余时间。
- 暂停/停止/重试。
- 失败原因和建议动作。
- 应用退出后的中断恢复。
- 资源策略：低资源、平衡、优先完成。

### 6.4 首次使用与恢复

必须覆盖：

- 首次启动环境检查。
- 选择资料目录并完成第一次预检。
- 没有 LibreOffice、磁盘不足、目录无权限。
- 数据库升级失败与自动回滚。
- 源文件被移动、删除或改名。
- 上次任务异常中断。
- 页库为空、搜索无结果、选片版本过期。

### 6.5 导出体验

组合导出应增加“导出前检查”：

- 页面尺寸是否一致。
- 源文件是否仍存在、哈希是否变化。
- 是否包含 HTML 页面。
- 是否包含外链、视频、OLE 或兼容性警告。
- 预计输出体积。

成功页提供：

- 打开文件。
- 在 Finder 中显示。
- 查看来源清单。
- 再次编辑当前选片单。
- 明确保真等级 A/B 及原因。

### 6.6 产品生命周期

成熟产品必须覆盖正常使用之外的完整生命周期：

| 阶段 | 产品能力 |
| --- | --- |
| 安装 | 独立安装包、系统要求、签名与可信来源 |
| 首次启动 | 环境自检、目录授权、首批导入、预计耗时和空间 |
| 日常使用 | 继续上次任务、搜索、选片、更新和导出 |
| 异常恢复 | 中断恢复、失效源处理、数据库修复、诊断包 |
| 数据迁移 | 修改数据目录、空间校验、复制校验、失败回滚 |
| 版本升级 | 数据库备份、兼容性检查、灰度、版本回滚 |
| 卸载 | 明确应用、缓存、索引和源文件分别如何处理 |

首次价值标准：新用户在无需阅读外部文档的情况下，15 分钟内完成目录导入、找到页面并
导出第一份新稿。

## 7. 工程化目标架构

### 7.1 当前主要问题

- `desktop/main.js` 同时承担窗口、IPC、子进程、调度和任务互斥。
- `renderer/app.js` 与 `auto-update.js` 使用全局状态和整块 DOM 重绘。
- `scan_plans.py` 同时承担验证、预检、仓储、执行和历史。
- 页库加载会重新生成并一次性读取完整 `catalog.json`。
- 桌面包仍依赖仓库目录、`.venv` 和外部 LibreOffice。
- 任务状态在 Electron 内存和 SQLite 运行记录之间尚未形成统一状态机。

### 7.2 目标分层

```text
Renderer
  ├─ library
  ├─ selection
  ├─ export
  ├─ automation
  └─ settings
        │ typed IPC
Electron main
  ├─ task coordinator
  ├─ scheduler
  ├─ filesystem grants
  ├─ updater
  └─ diagnostics
        │ CLI/RPC
Python application
  ├─ import service
  ├─ compose service
  ├─ scan-plan service
  ├─ storage service
  └─ health service
        │ repositories
SQLite + local assets + source files
```

### 7.3 必做重构

1. 将 Electron 主进程拆成 `ipc/`、`tasks/`、`scheduler/`、`security/`。
2. 将 renderer 按功能拆模块，集中管理任务状态和错误状态。
3. 将 `scan_plans.py` 拆为 config validator、repository、preview planner、runner。
4. 用持久化 job 状态机统一所有重任务，不只自动更新。
5. 页库改为分页查询和增量刷新，避免每次生成并读取完整 catalog。
6. 缩略图和预览采用临时目录生成、完整成功后原子替换。
7. 数据库迁移前自动备份，启动时执行 `integrity_check`。
8. IPC 全部校验 sender、参数 schema 和路径授权范围。

## 8. 性能与稳定性基线

### 8.1 性能预算

| 场景 | 目标 |
| --- | --- |
| 冷启动到可操作 | P95 < 3 秒 |
| 1 万页页库首屏 | P95 < 1.5 秒 |
| 搜索响应 | P95 < 150 ms |
| 未变化目录扫描 | 1000 文件 < 5 秒 |
| 自动更新 UI 事件延迟 | < 300 ms |
| 停止任务响应 | 当前文件后停止；强制上限 15 秒 |
| 组合导出额外体积 | 不保留未选页面依赖 |

### 8.2 稳定性目标

- 任务成功率 ≥ 99%。
- 崩溃后数据库可恢复率 100%。
- 源文件误删为 0。
- 相同输入重复执行不产生重复页。
- 所有失败都有错误码、用户文案和日志定位信息。

### 8.3 数据安全

- 所有源文件只读。
- 删除默认只操作索引和缓存。
- 数据目录迁移采用复制校验后切换。
- 日志默认脱敏用户名、绝对路径和 URL 参数。
- 自定义资源协议只能读取资产目录，不能读取任意绝对路径。

## 9. 发布与运维

成熟发布必须具备：

- 独立运行时，不依赖源码仓库和开发 `.venv`。
- macOS Developer ID 签名与 notarization。
- 自动更新渠道：内测、灰度、稳定。
- 数据库迁移备份与版本回滚说明。
- 首次启动环境自检。
- 一键导出诊断包。
- 崩溃日志和可选匿名性能指标。
- 版本发布说明和已知问题。

当前目录版 `.app` 已可构建；DMG 在当前沙箱中因挂载卷 `xattr` 权限失败。正式发布不能把
这个问题留给用户，应在 CI 或签名构建机完成 DMG、签名和公证。

## 10. 指标

### North Star

**每周成功完成的“找到页面 → 选片 → 导出”任务数。**

它比“导入页数”更接近用户真正获得的价值。

### 本季度 OMTM

**组合导出成功率与首次成功耗时。**

建议目标：

- 组合导出成功率 ≥ 98%。
- 从选片完成到获得文件 P95 < 60 秒。
- 导出失败后能通过产品内提示自行恢复的比例 ≥ 90%。

辅助指标：

- 周活跃页库数。
- 搜索后加入选片率。
- 自动更新成功率。
- 失效源比例。
- 预览修复率。
- 每 1000 页磁盘占用。

## 11. 产品增长与验证机制

推广不是发布安装包，而是验证用户能否独立完成核心闭环并形成重复使用。

### 11.1 转化漏斗

| 阶段 | 关键事件 | 建议指标 |
| --- | --- | --- |
| 获取 | 安装并首次启动 | 安装完成率 |
| 激活 | 完成首个目录导入 | 首次激活率、耗时 |
| 价值 | 搜索并加入至少一页 | 搜索到选片转化率 |
| 交付 | 成功生成新稿 | 组合导出成功率 |
| 留存 | 下一周再次搜索或导出 | 次周留存率 |
| 推荐 | 分享案例、模板或选片清单 | 主动推荐率 |

### 11.2 种子用户计划

- 首批只选择 10-20 位每周高频做稿用户。
- 覆盖大页库、复杂字体、视频、外链和跨文件组合等真实场景。
- 每位用户记录首次价值时间、失败点、人工协助次数和两周复用频次。
- 每周只解决阻塞核心闭环的问题，不被低频个性需求带偏。

### 11.3 产品反馈闭环

产品内提供三个反馈入口：

- 页面结果不对：关联 `slide_id`、版本和预览状态。
- 导出结果不对：关联 export manifest 和兼容性警告。
- 运行失败：关联任务、阶段和脱敏日志。

反馈必须自动携带上下文，避免用户重新描述环境，但上传前应明确展示将包含哪些信息。

### 11.4 决策门槛

- 若找页时间只下降不足 30%，优先重做检索与信息组织，不扩展团队能力。
- 若选片后导出率不足 30%，重新判断产品更像“参考库”还是“出稿工具”。
- 若首次独立激活率不足 80%，暂停高级功能，优先修安装、引导和环境依赖。
- 若自动更新确认率不足 60%，说明规则或信任表达不足，不增加更激进的自动化。
- 若两周复用用户不足 50%，不进入企业管理和商业化建设。

## 12. 产品演进边界

产品按三层演进，每一层达到门槛后才进入下一层：

| 层级 | 服务对象 | 核心能力 | 进入下一层的门槛 |
| --- | --- | --- | --- |
| L1 个人高频工作台 | 售前、市场、咨询、管理者 | 本地导入、搜索、可信判断、选片、导出、自动维护 | 10-20 位种子用户两周稳定复用 |
| L2 团队素材库 | 内容负责人和小团队 | 目录规范、共享标签、素材责任人、版本治理、团队模板 | 团队使用不依赖人工运维 |
| L3 企业级平台 | IT、管理员、客户成功 | 集中部署、权限、审计、策略、跨地域和服务体系 | 明确企业采购与管理需求 |

当前只建设 L1。以下能力暂不提前实现：

- 云端源文件托管。
- 复杂组织权限和审批流。
- 多人实时编辑。
- 企业级计费和配额。
- 通用数字资产管理。

国际化从 L1 开始保留基础能力：Unicode 路径、多语言内容检索、字体兼容和本地时区；
多语言 UI、Windows 支持和跨地域部署在 L2/L3 按真实需求推进。

## 17. 商业化与推广策略画布

### 成本定位

不与云端演示平台比最低存储成本，而是以“本地安全 + 页面级复用 + 原生导出”的独特价值
获得采用。成本重点控制在首次索引和高清预览；未变化文件的日常维护应接近零增量成本。

### 增长方式

第一阶段采用产品驱动增长：

1. 通过真实的“30 分钟找页变 3 分钟”案例获客。
2. 用本地处理和源文件不上传降低试用门槛。
3. 用可分享的选片清单、来源 manifest 和团队目录模板形成传播。
4. 种子用户先聚焦售前、市场与高频对客团队，不同时覆盖普通个人用户。

企业推广阶段再补充管理员部署、集中策略和客户成功服务，不提前建设完整 SaaS。

### 必备能力

- PPTX/OOXML 与 LibreOffice 渲染工程能力。
- 本地数据、任务和存储治理能力。
- 高密度桌面工作台设计能力。
- macOS 打包、签名、公证和升级能力。
- 面向真实大素材库的性能与兼容性测试能力。

### 防御性

真正难复制的不是“能搜索 PPT”，而是以下组合：

- 长期积累的页级本地索引和用户选片行为。
- 对复杂企业 PPT 的高保真渲染与原生组合兼容性。
- 对源文件、版本、移动、失效和历史的完整治理。
- 与真实方案生产流程融合，而不是单点 AI 功能。

### 策略一致性检查

- 本地优先与“不上传源文件”一致。
- 预检、来源清单和保真等级共同建立信任。
- 任务中心、存储中心和诊断能力共同支撑常态运行。
- 先聚焦高频做稿者，避免被通用文件管理需求稀释。
- 核心指标以成功复用和导出衡量，不以导入页数制造虚假繁荣。
