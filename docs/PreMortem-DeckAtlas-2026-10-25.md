# DeckAtlas 官网与公开 Beta 发布建议

## 当前放行判断：适合受控 Beta，公开自助发布尚有缺口

本次核对的公开提交为 `c1dc01a`。官网与该提交的 GitHub 质量门禁已成功；最近本地工作区门禁通过 376 个 Python 测试和 42 个桌面测试。两者覆盖的代码范围不同：新版 Agent 入库和跨进程操作锁仍是未提交工作区改动，不属于公开提交。以上检查不能替代干净 Mac 上的完整安装、真实渲染取消和旧库升级验收。

可以分享官网并邀请少量高频用户参与有协助的 Beta。尚不建议宣布面向普通用户的自助安装和完整发布已经就绪。以下是本次实际核对结果：

| 项目 | 观察结果 | 放行所需行动 |
| --- | --- | --- |
| 公开版本一致性 | `git show HEAD:src/pptlib/agent_cli.py` 不含 `import`；工作区版本包含该命令和新锁逻辑。当前网站将其标为新版预览 | 审查并固定要交付的功能提交，从同一提交构建桌面及 CLI，并核对实际能力 |
| 可下载产物 | GitHub Releases API 返回 0 个 Release；现有流程是源码安装 | 构建桌面包与完整 CLI 运行时包，验证后发布 Pre-release；官网接入真实下载 |
| 桌面路径授权 | `desktop/main.js` 的本地导入仅检查绝对路径等格式；`open-path` 与 `reveal` 检查主窗口 sender 和文件存在，未核对 dialog grants | 在主进程维护路径授权，来源和输出使用受认可记录；添加未经授权路径、失效授权和符号链接替换的拒绝测试 |
| 分发信任 | `packaging/after-pack.js` 在没有签名配置时仅作 ad-hoc 签名；未发现该发布的 Developer ID、公证及 Gatekeeper 验收证据 | 完成真实安装包签名公证及下载校验。首版可采用手动升级，不必先开发完整自动更新 |
| 首次使用与恢复 | 测试图明确保留干净机器安装、旧库升级、真实渲染取消与大库性能验收缺口 | 从仓库链接交给一个本机 Agent 开始，实际走完安装、依赖检查、打开、导入、检索、导出；同时验证停止恢复和旧库保留 |
| 许可 | `git ls-files` 未找到 LICENSE；GitHub license 接口返回 404，未检测到许可证 | 发布前确定源码使用许可并增加许可文件，核对分发依赖及演示素材授权 |

路径授权缺口的具体前提是可信窗口的 renderer 被攻破后发起请求；不能据此说远程用户目前可以直接访问任意机器，也不能把 sender 校验描述为完整文件权限保护。

最明显的体验优化是三项：提供真正可用的安装包及 Agent 安装入口；用脱敏 PPTX / HTML 样例让首次用户直接完成一轮复用；补一段真实的 Agent 检索与产物演示。还应明确可编辑 PPTX 只适用于兼容的 PPTX 选片，混合素材可以导出 HTML / ZIP，其中 PPTX 页以图片呈现，不暗示 HTML 会自动变成可编辑 PPT。

建议先修复路径边界并固定版本，验证安装和数据保护，再邀请 5–8 位用户完成两次真实任务。目标是能找页、能交付、愿意再次使用；Windows、跨设备同步、更多装饰和自动更新平台不必先做。

## 产品判断

DeckAtlas 应围绕一个可验证的价值组织产品与官网：把历史演示稿变成可按页检索、预览和重新组稿的本地资料库，并给 AI Agent 一个明确的读取与复用入口。

用户遇到的阻力有四段：大文件打开与翻页成本高；知道页内内容却难以跨文件定位；AI 缺少可调用的页库索引；找到页面后仍需跨稿搬运，新的稿件又散落到别处。官网应将每段困扰接到具体操作和结果。

大文件是检索的阻力，当前方案通过本地索引和预览减少日常反复打开整稿的需求。首次导入仍需解析和渲染，也会生成缓存。不能据此宣传文件压缩、零等待或没有新增存储占用。

单份 PowerPoint、部分系统索引及已有 AI 工具有自己的搜索或文件解析能力。DeckAtlas 的价值需要落在跨稿页面定位、来源追溯、可编辑组稿和稳定的 Agent 接口上，避免用“PPT 完全不能搜索”“AI 完全不能读 PPT”作为论据。

## 判断依据

- [Agent CLI 协议](../documentation/agent-cli.md)说明能力发现、页库查询、页面读取与受控组合导出；当前工作区的新版本还包括本地导入。官网和发布包必须以固定提交及实际 `capabilities` 对齐。
- [测试与发布验证图](../documentation/tests.md)仍记录文件路径授权、真实渲染子进程取消、升级和签名公证等发布缺口。自动化测试通过不等同于整套外部分发验收完成。
- [架构说明](../documentation/architecture.md)确认本地优先、源文件只读、确定性检索分类和私有桌面协议。没有证据支持任意自然语言理解、图像语义搜索或跨设备资料同步。
- 官网当前安装包与独立 CLI 下载入口待开放；HTML 与下一版 CLI 导入均有状态标注。公开 Beta 的承诺应由实际包的能力决定。

以下是建议与验收条件，不是已经完成的任务、实测结果或对外性能承诺。

## 官网的下一步

| 优先级 | 建议 | 用户获得什么 | 建议验收 |
| --- | --- | --- | --- |
| P0 | 在连环画之后补一段真实的短演示 | 看见搜到哪一页、怎样选片、最终导出了什么 | 使用脱敏素材，演示搜索、单页预览、跨稿选片、导出和重新打开；不做加速性能宣传 |
| P0 | 为桌面用户和 Agent 用户提供明确入口 | 普通用户能直接试用，Agent 用户能找到安装与使用方法 | 主入口指向可用的安装包或当前源码方法；CLI 专区保留简要步骤，长协议可另读 |
| P1 | 配套一个脱敏练习素材包 | 用户不必先导入自己的敏感大稿 | 用几份小稿提供关键词、目标页和选片示例；至少有可编辑 PPTX，另附 HTML 实验示例时说明环境 |
| P1 | 收紧首页的技术密度 | 先理解价值，再理解操作细节 | 首页保留一个 Agent 完整闭环；token、错误码和完整协议进入技术说明，始终保留跳转入口 |
| P1 | 在使用说明中明确来源与数据生命周期 | 知道移动源稿、删除缓存、升级和接入远程 Agent 的影响 | 解释源文件必须保留、缓存可管理；本地存储不代表外部 Agent 不会把读取内容发往它使用的服务 |

当前连环画解决的是“读者认出困扰”。下一块最有说服力的证据是完整产品操作与产物，而不是继续堆叠装饰图。AI 示例应展示真实检索结果、真实页面标识及实际导出，而不是只展示一个生成聊天框。

| 顺序 | 工作 | 影响 | 预计投入 / 主要不确定性 | 建议负责人 | 完成条件 |
| --- | --- | --- | --- | --- | --- |
| 1 | 固定发布范围与版本 | 避免官网、桌面包、CLI 包分别讲不同能力 | 中；新版导入与 HTML 是否进入公开 Beta 尚需确认和验收 | 产品 + 工程 | 固定提交、能力矩阵、版本与更新日志一致；用发布包运行 `capabilities` |

| 5 | 小范围 Beta，验证第二次使用 | 判断复用价值是否成立，而不仅是演示好看 | 小到中；尚无用户行为样本 | 产品 + 试用支持 | 建议邀请 5–8 名高频做方案的人完成两次真实任务，记录无需陪跑的成功率和不再使用的原因 |

先安排 1–4 中能直接影响试用闭环与数据安全的工作。Windows、跨设备同步、多模态分类和一整套自动更新系统可留到 Beta 反馈后评估。首版可以明确采用手动升级；更新来源可信和数据可恢复仍需验证。

## 假设两周后发布没有带来持续使用

### 有证据的发布风险

| 风险 | 分级 | 缓解与放行条件 |
| --- | --- | --- |
| 官网展示新版导入，发布的 CLI 却不支持 | 公开发布前处理 | 固定构建提交；安装包的能力发现、样例和官网状态逐项核对 |
| 用户下载后卡在依赖或签名弹窗 | 公开发布前处理 | 干净机器验收安装与首次导入，完成现有签名公证要求并给出依赖说明 |
| 升级指向新资料库，用户误以为数据丢失 | 公开发布前处理 | 旧版本真实数据目录与选片的升级测试；明确数据目录选择和恢复路径 |
| renderer 路径授权边界未闭合 | 公开发布前处理 | 关闭测试图中已记录的路径 grant 缺口，并验证拒绝未授权路径 |
| 真实渲染取消后留下子进程或不可恢复状态 | 公开发布前处理 | PPTX / HTML 真实任务取消、退出与重启测试；检查源文件、缓存和下一次任务 |

### 需要尽快验证的产品假设

- **索引建立后是否真的更省事？** 大稿首次导入可能是最重的步骤。分别测首次索引、再次搜索、浏览、缓存占用和取消恢复。把待定预算写在测试计划里，达成后再作为官网证据。
- **用户想找的内容是否有可提取文字？** 文字标题与备注可索引，图片中的文字和图表语义未必可搜索。用一组用户记得的内容测试，区分检索遗漏、图像信息和关键词差异。
- **AI 能力是否能降低人工操作？** 给一个已配置的本地 Agent 同一批素材，完成“搜案例 → 读页面 → 有序选片 → 预检导出”，观察仍需要多少次人工补上下文。
- **新稿是否会回到资料库？** 验证新版导入能否让第二次任务找到第一次的产物；保留源文件及依赖的操作是否清楚。

### 可以后续推进的事项

缺少 Windows 包、跨设备同步或多模态描述，不必阻止聚焦 Apple Silicon Mac 的有限 Beta。美术资源数量也不是放行标准。首版真正需要证明的是安装成功、页面找得到、导出能用、第二次仍愿意复用。

## 建议观察的指标

不上传源稿、路径或页面文本。可先通过用户自愿填写的试用记录和现场观察获得：

1. 首次成功复用率：启动后完成导入、找到目标页并导出的用户比例。
2. 目标页命中率：用户事先指出的目标页面能否通过常用关键词找到。
3. 两次任务的耗时：将首次建库耗时与之后查找耗时分开。
4. 导出可用率：在 PowerPoint 打开并确认页序、可编辑性和版式的比例。
5. 第二次主动使用率：是否在下一个真实任务继续使用同一个页库。

在建立基线后，再决定公开 Beta 的量化门槛。优先用这些证据验证核心价值，再扩大功能和平台范围。
